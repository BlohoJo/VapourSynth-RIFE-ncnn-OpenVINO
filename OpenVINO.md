Here is a break down of the OpenVINO / TBB support files, roughly in the order they get pulled into the process when you call `rifeov.RIFE()`.
 

### The OpenVINO half

**`openvino.dll`** is the OpenVINO runtime proper, the only one of the eight that `RIFE-OpenVINO.dll` links against directly. It contains `ov::Core` (the object the plugin creates), the graph representation (`ov::Model`), the graph-transformation passes, the tensor/shape machinery, and the plugin and frontend loaders. On its own it cannot run a single operation and cannot parse a single model file; it is the orchestrator that finds and drives the other DLLs below. If it is missing, Windows refuses to load the VapourSynth plugin at all ("The specified module could not be found", surfaced by VapourSynth as a plugin-load failure). Always needed.

**`openvino_intel_cpu_plugin.dll`** is the device backend, the thing that actually computes. When the plugin calls `core.compile_model(model, "CPU", ...)`, `openvino.dll` loads this DLL by name (statically registered since 2024, which is why there's no `plugins.xml` any more), hands it the graph, and this DLL lowers it to oneDNN kernels, picks the instruction set at runtime (AVX2 on your 9950X, AVX‑512 and the bf16 `inference_precision` path too, since Zen 4/5 expose AVX‑512 BF16), fuses ops, and executes `infer()`. Despite the "intel" in the name it is a generic x86‑64 backend; the AMD run in the first turn went through exactly this file. Always needed. The runtime download contains other backends too (`openvino_intel_gpu_plugin.dll`, `openvino_intel_npu_plugin.dll`, `openvino_auto_plugin.dll`, `openvino_hetero_plugin.dll` …); the CI deliberately ships only the CPU one, so `device="GPU"` will fail with a "device not registered" error rather than finding an Intel iGPU.

**`openvino_onnx_frontend.dll`** is a model parser. `core.read_model(path)` doesn't know how to read anything by itself; it inspects the file, asks each available frontend DLL "is this yours?", and the first that says yes converts the file into an `ov::Model`. This one handles `.onnx`, which is what `download_models.py` gives you, so for the default workflow it is needed. It is loaded lazily, i.e. only during `read_model`, so a missing frontend shows up as a *runtime* error ("Unable to read the model") rather than a plugin-load failure.

**`openvino_ir_frontend.dll`** is the same thing for OpenVINO's native IR format, the `.xml` + `.bin` pair that `scripts/convert_to_ir.py` produces. It is needed in two situations: if you pass an IR model path to `model_path`, and — less obviously — whenever `cache_dir` is set. The compiled-model cache is stored in a serialized form that goes back through the IR reader on load, so without this DLL the cache silently falls back to a full recompile, or errors, depending on version. Keeping both frontends costs a couple of megabytes and avoids that class of surprise. The other frontends in the runtime (`openvino_tensorflow_frontend.dll`, `openvino_pytorch_frontend.dll`, `openvino_paddle_frontend.dll`, `openvino_tensorflow_lite_frontend.dll`, `openvino_jax_frontend.dll`) are irrelevant to RIFE and are not shipped.
 

### The TBB half

OpenVINO's CPU plugin is built on Intel oneTBB for all of its threading: the stream/thread pool, the parallel loops inside oneDNN kernels, and the task arenas that `hint="throughput"` / `num_requests` carve out. It does not use the Windows thread pool or OpenMP, so TBB is a hard dependency even though your plugin code never mentions it.

**`tbb12.dll`** is oneTBB itself (the "12" is the ABI version, unrelated to the product version). It is a direct import of both `openvino.dll` and `openvino_intel_cpu_plugin.dll`, so like `openvino.dll` it must be present or nothing loads. This is also the one that's easy to get wrong: if a different `tbb12.dll` is already loaded in the VapourSynth process by another plugin (or sitting earlier in the DLL search path), that copy wins, and an older oneTBB can be ABI-incompatible with what OpenVINO was built against. The CI packaging ships the exact `tbb12.dll` from the same OpenVINO release next to the plugin for that reason.

**`tbbbind_2_5.dll`** is TBB's hardware-topology helper. It wraps hwloc and lets TBB pin task arenas to specific NUMA nodes or core types; OpenVINO uses it for its "pin threads to cores" scheduling and for separating P‑cores and E‑cores on hybrid Intel CPUs. `tbb12.dll` loads it dynamically at startup and carries on without it if it isn't there, so it is optional in the strict sense. On a 9950X (single NUMA node, homogeneous cores) its practical effect is small, but OpenVINO's CPU plugin does query it to build its core map, and I'd rather ship the 100 KB than reason about which scheduling heuristics degrade without it. The `_2_5` suffix is the hwloc API version it was built against; some runtime builds ship a `tbbbind_2_0`/`tbbbind` sibling as well, and the CI copies whatever name the release actually contains.

**`tbbmalloc.dll`** is TBB's scalable memory allocator, a per-thread-cached allocator designed to avoid lock contention when many threads allocate at once (which is exactly what a 16-core inference does during compile and with multiple in-flight requests). oneDNN and the CPU plugin can use it for internal scratch buffers. It is not a static import, so its absence doesn't prevent loading; it reduces allocator contention when present.

**`tbbmalloc_proxy.dll`** is the aggressive variant: when loaded into a process it redirects *every* `malloc`/`free`/`new`/`delete` in that process to `tbbmalloc`, by patching the CRT. Nothing in OpenVINO or the plugin loads it automatically; it's an opt-in tool you'd inject deliberately (for instance by linking against it or via a `TBB_MALLOC_*` env var) to measure whether a global allocator swap helps. In a host process like VapourSynth, which already has its own frame allocator and plenty of other plugins, I would not want that behaviour silently enabled. It is in the package because the CI copies the complete TBB set that the OpenVINO release ships, so the folder is self-consistent, not because the plugin uses it. If you want the minimal set, it's the one file you can delete with a clear conscience.
 

### The short version

Strictly required to load and run an ONNX model on CPU: `openvino.dll`, `openvino_intel_cpu_plugin.dll`, `openvino_onnx_frontend.dll`, `tbb12.dll`. Required additionally if you use IR models or `cache_dir`: `openvino_ir_frontend.dll`. Optional performance helpers that TBB picks up if present: `tbbbind_2_5.dll`, `tbbmalloc.dll`. Shipped for completeness, unused unless you deliberately enable it: `tbbmalloc_proxy.dll`. Everything except the proxy stays in the package on purpose, because the two "optional" TBB pieces change scheduling and allocation behaviour in ways that only show up as unexplained performance differences between machines, and the whole set is about 2 MB on top of the ~60 MB that `openvino.dll` plus the CPU plugin already weigh.

Two things I haven't verified on Windows and am stating from the Linux build and the OpenVINO source rather than from a trace of your machine: the exact moment the CPU plugin probes `tbbbind`, and whether `tbbmalloc` is actually picked up by the 2026.x CPU plugin without an explicit setting. If you ever want certainty, Process Explorer or Process Monitor on `vspipe` during a first frame will show which of the eight actually get mapped.

---

Breakdown given above: four files are hard requirements (`openvino.dll`, the CPU plugin, the ONNX frontend, `tbb12.dll`), the IR frontend is needed for `.xml` models or `cache_dir`, `tbbbind` and `tbbmalloc` are optional TBB performance helpers, and `tbbmalloc_proxy.dll` is shipped only for completeness and is never used unless deliberately enabled.
